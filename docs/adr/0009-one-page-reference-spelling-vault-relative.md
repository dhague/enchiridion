# Pages are addressed by one vault-relative spelling — "page reference", never a separate wiki-relative one

Three address conventions coexisted in the script layer, each crossing a hand-written string edit in a caller ([#123](https://github.com/dhague/enchiridion/issues/123)): **vault-relative** (`wiki/concepts/a.md`, used by `place`, `Vault`, `ingest`, `commit`, `chain_of_evidence`), **wiki-relative** (`concepts/a.md`, used by `search_index`, `page_record`, and so `discover`), and a third thing — `page_record._rebase_to_wiki_root` returned a path its own docstring labelled a "Trap", one `..` short of true vault-relative and only correct because `ingest_scan._back_pointers_by_raw` re-resolved it with a `prefix="wiki"` that cancelled the missing `..`. The seam had already leaked: `discover.DiscoveryCandidate.rel` arrived wiki-relative, but `skills/wiki-ingest/SKILL.md` step 3 told the model to use it directly as an `op: "update"` target that `ingest.validate` requires vault-relative — the `wiki/` prefix was an unwritten step between two tool calls, with a plan-validation error as the failure mode and no test covering it.

We decided there is **one spelling: vault-relative**, everywhere, and it is named a **page reference** (see `CONTEXT.md`). The wiki-relative spelling ceases to exist in the codebase, not merely "owned by one module": the search index's `SCHEMA_VERSION` bumps and its `page` table stores vault-relative `page_ref` as primary key (the bump's delete-and-rebuild migration absorbs it), `_scan`/`_reindex_walk` compute rels via `relative_to(root)` instead of `relative_to(root/"wiki")`, `_compute_git_dates`'s `wiki/` strip is deleted, `page_record` takes vault-relative rels so its edge targets resolve true vault-relative by construction (the `_rebase_to_wiki_root` trap and `ingest_scan`'s cancelling `prefix="wiki"` both die), and every `removeprefix("wiki/")` / `f"wiki/{...}"` prepend in `vault.py` is deleted. `wikipage.resolve_link_dest`'s default `prefix` flips to `""` — its `"wiki"` default existed only for the old convention. The field is renamed `rel` → `page_ref` across code, the DB column, the plan JSON field, CLI output, and SKILL.md's step-3 instruction.

We deliberately did **not** build the "address module" — working name `PageRef` — that the issue originally proposed. Its stated purpose was a type "that refuses to be a bare `str`", preventing accidental mixing of two spellings. With one spelling left, there is nothing to mix, and a wrapper would be unenforced anyway (the repo runs no type checker). The issue's own deletion test — *"delete PageRef and the conversion reappears at six call sites"* — is now inverted: there are zero conversions left to concentrate, so a `PageRef` type would fail its own earn-its-keep test. A vault-relative path under `raw/` is not a page reference (it names a raw artifact) and keeps its separate names (`raw_rel`, `plan.raw`, `raw_source`).

## Consequences

- A discover candidate's `page_ref` is now directly usable as an `IngestPlan` `rel`/edge target, so `SKILL.md`'s step-3 instruction is literally true and the `Vault.search` docstring's wiki-relative caveat is deleted rather than documented.
- The schema spelling change is the one hard part: existing vaults rebuild their `.wiki-knowledge/index.db` on next open (delete-and-rebuild is the designed migration strategy, `index.db` is gitignored, and the staleness scan at ~2000 pages is ~50ms).
- Raw artifacts and pages share the vault-relative spelling but are different address-spaces; code keeps them visibly separate (`page_ref` vs. `raw_rel`/`raw_source`) so the glossary boundary is not re-blurred.
